Hmssql.Query.Internal

Description

What Hmssql.Query and Hmssql.BatchQuery share beyond the types of Hmssql.Query.Types: encoding a query into its sp_executesql call, reading a response step by step, decoding result sets from a reader, and packing statements into messages. Applications use Hmssql.Query, which re-exports readStep, drainResponse and paramNameProblem; nothing here is stable.

paramNameProblem :: Text -> Maybe String Source #

Why a parameter name can't be used, if it can't: it must be a T-SQL variable name, @ followed by one or more letters, combining marks, decimal digits, @, #, $ or _ (Unicode ones included, but only from the Basic Multilingual Plane: SQL Server rejects surrogates in identifiers). The query functions' parameter names are spliced into the sp_executesql declaration, where anything else (a space, a comma, a parenthesis, a comment) would change what is declared. callProcedure doesn't use this check: its parameter names are sent as data, and the server reports the ones it can't match. SQL Server itself accepts a few more names (a bare @, and ignores format characters such as U+200D and trailing spaces in RPC parameter names), and rejects some letters added in recent Unicode versions; it enforces its 128-character limit itself.

readStep :: ResponseReader -> RowRead r -> IO (ResponseStep r) Source #

The next thing in the response (nextStep), with the rows decoded by the given function: a batch of rows, a token other than a row or a nonfatal ERROR (withheld), or StepEnd, which throws the withheld error (or SevereError) instead if there was one. A response that ends with the connection closed after an error (by the server, as after a severity 20 error, or by a failed transport) throws that error; after close, the ConnectionClosed that every use of the connection gets. (The withheld error is the reader's, not a stream's: a stream run again from a step before the error would otherwise report an error it hadn't seen.)

A fatal ERROR is thrown by the common token reader immediately and leaves the connection broken.

Reading one statement of a batch query (respBatch): the statement's DONEPROC is returned and then StepEnd, for as long as the statement stays the current one; an ERROR token isn't withheld but ends the batch (scopeFail), and the response's end throws SevereError for a failed DONE but never a withheld error, which there is none of.

ignoreRows :: RowRead () Source #

Skip the rows without decoding them. A row before the first COLMETADATA is a ProtocolError, since there are no columns to skip it by, so the result-set loops need no state for that case.

drainResponse :: ResponseReader -> IO () Source #

Read the rest of the response and discard it. The withheld error, if any, is thrown at the end. Nothing to do once the end has been read.

yieldRows :: ResponseReader -> [r] -> Stream (Of r) IO () -> Stream (Of r) IO () Source #

Yield the rows of a batch, then continue. Before each row, the response must still be the current one (checkCurrent): the rows of a batch are read from the connection together, but a stream whose response was superseded by a later request (or canceled, or drained) throws ResultAbandoned at the next row it is asked for, not after the rows it already had.

foldFirstResultSet :: RowCompiler r -> ResponseReader -> a -> (a -> r -> IO a) -> IO a Source #

Fold over the rows of the first result set, a batch at a time, then drain the rest of the response. A row that doesn't decode drains the rest of the response before its DecodeError is thrown. Before each call of the step, the response must still be the current one (checkCurrent, as a queryS stream checks before each row): a step that abandons it (by making another request on the connection, or closing it) is the last to run, and the fold throws ResultAbandoned rather than run the steps for the rest of the batch it had.
